## Approach decision: thin API (not auth.users trigger)

**Pick: thin Next.js bootstrap API + SQL tables/RLS. No `auth.users` INSERT trigger in F2.3.**

| Option | Verdict |
|---|---|
| **A. DB trigger on `auth.users` INSERT** | Rejected as primary. Prior Nomade style is migrations + deny-by-default RLS + server `service_role` routes (F1.3–F1.8). A trigger cannot return F2.1 merge hints (needs client `hasLocalDraft`) or stable HTTP error codes. Dual writers (trigger + API) risk race/drift. |
| **B. Thin API `POST /api/account/bootstrap`** | **Chosen.** Locked by F2.1 §5 happy path and §10 surface. Next.js verifies env-scoped JWT, upserts via `service_role`, returns `{ userId, created, merge }`. Matches stack ownership (this repo owns auth verification). |
| **C. Edge Function only** | Rejected for V1. Would invent a second runtime beside existing App Router APIs (`/api/health`, etc.). |

**UUID mapping (F2.1 §3 — document here):**  
`internal.users.id` **is the same UUID as** `auth.users.id` (FK `references auth.users (id)`). Do **not** mint a second app UUID. JWT `sub` → app `userId` with no indirection table for the auth user itself. `auth_identities` binds Apple `provider_subject` to that same `user_id`.

**Why not put tables in `api`:** F1.2/F1.3 keep domain data under `internal`; `api` is explicit PostgREST surface with smoke-only today. Bootstrap is server-mediated (`service_role`); iOS never talks PostgREST to identity tables in V1.

No new ADR: F2.1 already froze semantics; this runbook only records schema placement + API-vs-trigger.

## Schema proposal

Class B (F0.2). Names match F2.1 (`users`, `auth_identities`). **No** `profiles` table here — journey profiles are Class C / F4.

### `internal.users`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` PK | `= auth.users.id`; `references auth.users (id)` |
| `email` | `text` NULL | Apple-relay optional; **never** UNIQUE as account key; **never** used alone for authz |
| `deletion_status` | `text` NOT NULL DEFAULT `'active'` | Check: `active` \| `pending_deletion` \| `deleted` — columns ready for F2.6; no wipe job in F2.3 |
| `deleted_at` | `timestamptz` NULL | Set by F2.6 |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |
| `updated_at` | `timestamptz` NOT NULL DEFAULT `now()` | Maintain via trigger or API write |

Comments in SQL: Class B; F2.1; no email PK.

### `internal.auth_identities`

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` PK DEFAULT `gen_random_uuid()` | Surrogate |
| `user_id` | `uuid` NOT NULL | FK → `internal.users (id)` |
| `provider` | `text` NOT NULL | V1: `'apple'` only (check constraint or app enforce + comment) |
| `provider_subject` | `text` NOT NULL | Opaque Apple `sub`; store raw text; **never** log full value (prefix only) |
| `email` | `text` NULL | Snapshot at link time; nullable |
| `created_at` / `updated_at` | `timestamptz` | |
| `closed_at` | `timestamptz` NULL | NULL = active; set on deletion close (F2.6) so re-signup can insert a new row / new `users.id` |

**Unique while active:**

```sql
create unique index auth_identities_provider_subject_active_uidx
  on internal.auth_identities (provider, provider_subject)
  where closed_at is null;
```

### Grants + RLS

- `REVOKE ALL` from `anon` / `authenticated` on both tables (reinforce F1.3).  
- `GRANT ALL` to `postgres`, `service_role` only.  
- `ENABLE ROW LEVEL SECURITY` on both; **zero** policies for client roles (deny-by-default even if someone grants later).  
- Optional later (not F2.3): `api` view/RPC with explicit grants — out of scope.

### Schema must not block Case A/B

- Bootstrap response includes `merge.case` ∈ `A|B|C|D` per F2.1 §7.  
- F2.3 **does not** implement journey upload or Case B UI.  
- Until journey tables exist: treat “has server journey” as **false** (so Case B cannot fire yet). Document stub: when F4 adds journey rows, bootstrap (or a later helper) sets `hasServerJourney` from `exists(journey… where user_id = …)`.  
- Client may send `hasLocalDraft: boolean`; Case A/C/D logic still works; Case B returns `MERGE_REQUIRED` only when both local draft **and** server journey are true.

### Out of this migration

- Journey / billing / devices tables  
- Soft-delete wipe jobs (F2.6)  
- PostgREST exposure of identity  
- `auth.users` trigger  
- Prod apply

## API proposal — `POST /api/account/bootstrap`

### Contract (F2.1 §5 / §10)

**Auth:** `Authorization: Bearer <supabase access JWT>` for the **current env** (`local` / `nomade-dev` Preview — never accept prod tokens on Preview).

**Request body (JSON, all optional except as noted):**

```json
{
  "hasLocalDraft": false
}
```

Do **not** accept Apple identity tokens or authorization codes in this body — Supabase already established the session; subject comes from verified JWT / `auth.users` + identities metadata via service client.

**Success 200:**

```json
{
  "userId": "<uuid>",
  "created": true,
  "merge": {
    "case": "C",
    "hasLocalDraft": false,
    "hasServerJourney": false
  }
}
```

`created: true` iff this call inserted the `internal.users` row (first bootstrap). Retries with same Apple subject → same `userId`, `created: false`, `merge.case: "D"` when identity already linked.

**Errors:** F1.8 envelope `{ error: { code, message, requestId } }` + `x-request-id`.

| Code | HTTP | When |
|---|---|---|
| `UNAUTHENTICATED` | 401 | Missing/invalid/expired/wrong-env JWT |
| `ACCOUNT_PENDING_DELETION` | 403 | `deletion_status = pending_deletion` |
| `ACCOUNT_DELETED` | 401/410 | Identity closed / user deleted |
| `MERGE_REQUIRED` | 409 | Case B (when journey exists later) — still return `userId`; client must not sync upload until choice |
| `BAD_REQUEST` | 400 | Malformed JSON |
| `INTERNAL_ERROR` | 500 | Unexpected |

Success bodies never echo Authorization headers, refresh tokens, service-role keys, or raw Apple tokens.

### Handler sketch (Theo implements)

1. `getRequestId` + `log.child` (F1.8).  
2. Parse Bearer; verify JWT with **env** Supabase JWT secret / JWKS (`nomade-dev` vs local vs prod — prod path unused in F2.3). Minimal helper under `src/lib/auth/` is OK; F2.5 extracts shared middleware later — **do not** block F2.3 waiting on F2.5 polish.  
3. Resolve `auth.users.id` (= JWT `sub`). Load Apple identity from Supabase Auth admin/user API or JWT `app_metadata` / `identities` as available; require `provider === 'apple'` and a `provider_subject`.  
4. With `createServiceClient()` (`service_role`):  
   - Upsert `internal.users` on `id = sub` (email nullable from Auth user if present).  
   - Upsert `internal.auth_identities` for `(provider, provider_subject)` active unique; on conflict with **different** `user_id` → hard fail `INTERNAL_ERROR` / conflict (should not happen if uniqueness holds).  
5. Compute merge case (A/B/C/D); return JSON.  
6. Logs: `requestId`, `userId`, allow/deny codes — never full `sub`, email, or tokens.

Optional companion in same PR (nice-to-have, still one task): stub `GET /api/account/me` returning `{ userId, createdAt, deletionStatus }` — only if cheap; otherwise leave for a follow-up under F2.5/F2.6.

### Idempotency tests

- Same JWT twice → same `userId`, second `created: false`.  
- Concurrent double-bootstrap → unique index + upsert; no duplicate users.  
- Email change / null email must not create a second user.
