## Goal

Wire **Sign in with Apple token revocation** so in-app account deletion (F2.6 / F2.6b) also invalidates the user’s Apple authorization for Nomade — the gap App Review often flags for SIWA apps under **5.1.1(v)** / [Offering account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app).

**Complete when:**

1. Human (Isaias) creates a **Sign in with Apple Key** (`.p8`) on Apple Developer, enables it for App ID **`com.izaya.Nomade`**, stores Team ID / Key ID / `.p8` in **Keeper** (never chat/git).  
2. Backend (`nomade-dev` / Preview / local only): on soft-delete, when iOS supplies a fresh Apple **`authorizationCode`**, server generates a short-lived **client_secret JWT**, exchanges the code at Apple `/auth/token`, then **revokes** the resulting refresh token at `/auth/revoke`.  
3. Soft-delete still closes `auth_identities` + sets `pending_deletion` as today; hard purge (F2.6p) stays Auth `deleteUser` + scrub — **no** Apple revoke in cron (codes expire; no stored Apple refresh tokens today).  
4. Thin iOS companion: the existing F2.6b SIWA reauth before delete **captures `authorizationCode`** and sends it on `POST /api/account/delete`.  
5. Unit tests green (mocked Apple HTTP); CI green; docs landed; **`nomade-prod` untouched**; no secrets in draft/PR/chat.  
6. Production Apple Key / Vercel prod env / prod revoke → **explicitly deferred** (separate human gate).

## Cap defaults (locked proposals — Isaias can approve as-written)

Cap’s **proposed defaults** are in **bold**. Approve means Theo (and iOS companion) may implement against these without re-design.

### A. When to revoke

**Pick: revoke on soft-delete (`POST /api/account/delete`), not on hard purge.**

| Option | Verdict |
|---|---|
| **A. Soft-delete path (user-initiated), using fresh `authorizationCode` from iOS SIWA reauth** | **Chosen.** Matches App Review expectation at deletion time; codes expire ~5 minutes; F2.6b already reauths SIWA. |
| B. Hard purge cron only | Rejected — too late for auth codes; we do not store Apple refresh tokens today. |
| C. Both soft-delete and purge | Rejected — purge has nothing useful to revoke unless we add long-lived token storage (out of V1). |

Hard purge continues to Auth `deleteUser` + scrub only (F2.6p). Re-SIWA after Auth delete still mints a new UUID.

### B. `client_id`: App ID vs Services ID

**Pick: App ID / bundle ID `com.izaya.Nomade` as `client_id` and as JWT `sub`. Do not create a Services ID in F2.6r.**

| Option | Verdict |
|---|---|
| **A. App ID (`com.izaya.Nomade`)** | **Chosen.** Apple docs allow App ID **or** Services ID; native iOS authorization codes are issued for the App ID. Services ID would mismatch native codes and revises F2.2 ADR for no gain. |
| B. Create Services ID + Return URLs for revoke-only | Rejected — OAuth surface + wrong `aud`/`client_id` for native codes. |
| C. Create Services ID now “for future web” | Rejected — needs ADR revision + 6-month secret ops; not required to close revoke. |

**F2.2 ADR amendment (docs-only):** native login still needs no Services ID; F2.6r **does** require a Sign in with Apple **Key** (`.p8`) for REST client_secret — previously skipped. Login path unchanged.

### D. Where the Key lives

**Pick:** Apple Developer → Keys → **Sign in with Apple** Key, enabled for App ID `com.izaya.Nomade`; download `.p8` **once** into Keeper; never commit; never put in iOS app bundle; server-only (Next.js).

### E. JWT `client_secret` generation (server)

Generate per revoke attempt (or short cache ≤1h — Cap default: **generate fresh each call**, keep code simple):

```text
Header:  { "alg": "ES256", "kid": "<APPLE_KEY_ID>" }
Payload: {
  "iss": "<APPLE_TEAM_ID>",
  "iat": <now_unix>,
  "exp": <now_unix + 3600>,          // Cap default: 1 hour (Apple max ≤ ~6 months)
  "aud": "https://appleid.apple.com",
  "sub": "<APPLE_CLIENT_ID>"         // com.izaya.Nomade
}
Sign: ES256 with APPLE_PRIVATE_KEY (P-256). Prefer `jose` (or existing JWT lib) — ensure raw R||S signature form Apple accepts.
```

Never log the JWT. Never commit fixtures containing a real signed secret.

### F. Call site + sequence

**Pick: soft-delete route / helper — before marking `pending_deletion` when a code is present.**

Per `POST /api/account/delete` (active → pending):

1. `requireAccess` → `userId`.  
2. Validate `confirm: "DELETE"`.  
3. If body includes non-empty `appleAuthorizationCode` (string):  
   a. Build client_secret JWT.  
   b. `POST https://appleid.apple.com/auth/token` with  
      `client_id`, `client_secret`, `code`, `grant_type=authorization_code`  
      (omit / empty `redirect_uri` for native).  
   c. Take `refresh_token` (prefer) or `access_token` from response.  
   d. `POST https://appleid.apple.com/auth/revoke` with  
      `client_id`, `client_secret`, `token`, `token_type_hint=refresh_token` (or `access_token`).  
   e. Apple `200` empty body = success (also OK if already revoked).  
4. Then existing soft-delete: set `pending_deletion`, `deleted_at`, close `auth_identities`.  
5. Return success shape (extend optionally with `appleRevoked: true|false` — Cap default **include boolean** for client/smoke; never include tokens).

**Do not** call Apple from purge cron. **Do not** change Auth `deleteUser` timing.

Idempotent replay while already `pending_deletion`: **skip** Apple revoke (no second code); return same 200 as today.

### G. Failure policy

**Pick: hard-fail soft-delete when the client sent a code and exchange/revoke fails; best-effort skip only when no code.**

| Case | Behavior |
|---|---|
| `appleAuthorizationCode` present + Apple exchange/revoke **fails** | **Do not** soft-delete. Return `502` / `503` with F1.8 code e.g. `APPLE_REVOKE_FAILED` (add to shared ERROR_CODES). Structured warn: outcome only — no code/token. |
| `appleAuthorizationCode` present + Apple config missing | Same hard-fail (`APPLE_REVOKE_MISCONFIGURED` or reuse `APPLE_REVOKE_FAILED`). |
| Code **absent** (old client / curl smoke without code) | Soft-delete proceeds; log `appleRevokeSkipped`; response `appleRevoked: false`. **App Review path must use current iOS that sends the code.** |
| Already `pending_deletion` | Idempotent 200; skip revoke. |
| User has no Apple identity row | Soft-delete OK; skip revoke if no code (V1 is Apple-only anyway). |

Cap default for App Review readiness: **iOS companion is in-scope** so production delete always sends a code.

### H. iOS changes

**Pick: thin companion on `nomade-ios` — reuse F2.6b SIWA reauth; forward `authorizationCode`.**

1. During delete reauth, keep the Apple `ASAuthorizationAppleIDCredential.authorizationCode` (UTF-8 string).  
2. Extend delete request body:  
   `{ "confirm": "DELETE", "appleAuthorizationCode": "<code>" }`.  
3. If user cancels SIWA → abort delete (already F2.6b).  
4. If backend returns `APPLE_REVOKE_FAILED` → show retryable error; do **not** claim deletion scheduled.  
5. No `.p8` on device; no Services ID; no new entitlement beyond existing SIWA.

Backend may merge first with code-optional; iOS companion must land before claiming App Review SIWA-revoke readiness.

| Risk | Mitigation |
|---|---|
| Using Services ID as `client_id` with native auth codes → `invalid_client` | Cap default App ID only; document loudly |
