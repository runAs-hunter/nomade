## Goal

Turn F2.3’s **minimal** Bearer verify helper into a **shared, documented auth layer** for protected App Router routes — without inventing a second auth stack or breaking anonymous chat.

**Complete when:**

1. Shared helper(s) under `src/lib/auth/` implement F2.1 §6 for route handlers: require Bearer → env-scoped verify → `userId` / `User` / token; map failures to F1.8 `UNAUTHENTICATED` (401).  
2. `POST /api/account/bootstrap` uses the shared helper (behavior unchanged for clients).  
3. At least one additional protected account route uses the same helper (prefer thin `GET /api/account/me` — see Approach).  
4. Explicit **route classification** table in docs: which routes are public vs require auth (chat/route stay public in F2.5).  
5. Unit tests for the helper + bootstrap still green; CI `lint` / `test` / `typecheck` / `build` green.  
6. Docs PR: runbook + short `docs/auth-api.md` (or extend `identity-bootstrap.md`); **no secrets in git/chat**; **nomade-prod / prod Auth untouched**.

## Approach decision

### A. What “middleware” means in F2.5

**Pick: App Router shared helper + thin wrappers — not Next.js Edge `middleware.ts` as the primary gate.**

| Option | Verdict |
|---|---|
| **A. Next.js Edge `middleware.ts` requiring JWT on `/api/*`** | Rejected as primary. Edge + Supabase `getUser` needs a different client story; blanket `/api/*` auth would break health + anonymous chat/route. High blast radius. |
| **B. Shared `requireAccess` / `requireVerifiedAccess` helper for route handlers** | **Chosen.** Matches existing Node route handlers + `server-only` verify module. Routes opt in. Easy to test. Same envelope as bootstrap. |
| **C. jose + raw JWT secret / JWKS in every route** | Rejected for F2.5. Duplicates Auth; needs new env (`JWT_SECRET`) Cap/Theo must not handle in chat; F2.3 already chose getUser. Revisit only if getUser fails a concrete F2.1 claim (iss/aud) we cannot cover otherwise. |

Optional later (out of F2.5): Edge middleware that only **strips** or **tags** requests — never the sole verifier.

### B. Soft vs hard auth on chat

**Pick: chat + route remain public in F2.5.**

Anonymous local-only use (F2.1) still talks to `/api/chat` and `/api/route` without Apple. Forcing Bearer now breaks F2.4-era product behavior. Future F3/F4 may add **optional** Bearer (attach `userId` when present) or hard-require after entitlement — separate task.

### C. Extra protected route

**Pick: add thin `GET /api/account/me` using the shared helper** (F2.3 noted this as nice-to-have).

Response sketch (no PII beyond what F2.1 allows for account):

```json
{
  "userId": "<uuid>",
  "deletionStatus": "active",
  "emailPresent": false
}
```

Rules:

- Require Bearer + verified access (shared helper).  
- Load `internal.users` via **service_role** (same pattern as bootstrap); map missing row → `UNAUTHENTICATED` or `404` with stable code — **prefer** `UNAUTHENTICATED` / “call bootstrap” only if product wants bootstrap-first; otherwise `404` `NOT_FOUND` if we already have that code, else keep bootstrap-required message under `UNAUTHENTICATED` for consistency with “no app user yet”. **Decision for Theo:** if no `internal.users` row → **401 `UNAUTHENTICATED`** with message “Bootstrap required” (clients must bootstrap before me).  
- Never return full email in F2.5 (use `emailPresent: boolean` only).  
- Never log JWT / full Apple sub (use `subjectPrefix` if needed).

If `me` threatens scope, Cap may approve **helper-only PR** without `me` — document in reply checklist.

## Implementation sketch (Theo)

### 1. Shared helpers (`src/lib/auth/`)

Keep `verify-access-token.ts`. Add (names flexible):

- `requireAccess(request: Request | NextRequest): Promise<VerifiedAccess | NextResponse>`  
  - Calls `verifyAccessToken(authorization)`  
  - On fail → F1.8 JSON 401 `UNAUTHENTICATED` + `requestId` + structured log (`reason: missing|invalid`) — **no token bodies**  
  - On ok → return `VerifiedAccess`  
- Optional: `assertSameUser(authUserId, resourceUserId)` → 403 `FORBIDDEN` (for future IDOR checks; can ship with unit test even if unused by routes yet)

Refactor bootstrap to call `requireAccess` (or equivalent) instead of duplicating verify + 401 branches.

### 2. `GET /api/account/me`

As above. Unit/integration tests with mocked service client + verify.

### 3. Docs

- `docs/runbooks/F2.5-jwt-middleware-polish-runbook.md` (this file, or Cap-approved copy)  
- Short `docs/auth-api.md`: route classification table + “how to protect a new route” (3–5 lines + import example)  
- Pointer in `AGENTS.md` / `identity-bootstrap.md` if needed  

### 4. Tests

- Expand `verify-access-token` / new `requireAccess` tests: missing header, bad token, happy path  
- Bootstrap tests still pass (behavior unchanged)  
- `me` tests: 401 without Bearer; 401 invalid; 200 with user row; 401 when Auth ok but no `internal.users` row (bootstrap required)
