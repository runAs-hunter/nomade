## 1. Decision summary

Nomade runs four environments: **local**, **development**, **staging**, **production**.

| Rule | Policy |
|---|---|
| Database isolation | One Supabase project (or approved Supabase branch) per environment. Never share production data with agents or MCP. |
| Agent / MCP access | Development only; prefer `read_only` for routine work. Production MCP disabled. |
| Schema changes | Reviewed migration files in `runAs-hunter/nomade` only. No ad hoc Dashboard DDL after F1.2. |
| Production deploys | Human-gated (Vercel/GitHub environment approval). Agents prepare; owner promotes. |
| Client secrets | iOS/web clients never receive service-role keys. Publishable keys only, with tested RLS / explicit grants. |
| Knowledge vs customer data | Same Postgres host per env; separate schemas/roles per F0.1 / F0.2. |

**Recommended staging strategy (needs your checkbox in §8):** create a dedicated Supabase **staging** project (and later **production**), rather than using Supabase preview branches as the long-term model. Preview branches remain optional for short-lived experiments after F1 is stable.

## 3. Promotion rules

### 3.1 Development → Staging

1. Task branch `task/<id>-…` → PR into the integration branch/`main` per repo conventions.  
2. Required checks green (once F1.5 / F1.6 exist): lint, typecheck, tests, build; backend also migration reset where applicable.  
3. Preview deploy healthy (F1.7).  
4. Owner or designated reviewer approves merge.  
5. Staging deploy runs automatically from the protected branch **or** via approved workflow dispatch.  
6. Smoke: health check, auth path (when built), no production secrets in staging env.

### 3.2 Staging → Production (human gate)

Required before any production migration or App Store release train step:

| Check | Owner |
|---|---|
| Staging smoke passed for the release candidate | Engineering + Isaias |
| Migrations reviewed; rollback notes in PR | Migration owner |
| No service-role key in client bundles | Reviewer |
| Privacy / AI disclosure still match behavior (after F2.8) | Isaias |
| Billing/sandbox matrix recorded when billing ships (F3.9) | Isaias |
| Explicit “promote” approval recorded (PR comment, release ticket, or this matrix changelog) | Isaias |

Agents may prepare commands, PRs, and checklists. They must **not** approve production promotion or install production secrets.

### 3.3 Knowledge content promotion (separate from code)

| Path | Rule |
|---|---|
| Candidate claims | Never customer-answerable |
| Approved claims | Human review (primary + independent second for high-risk) per K0.7 / K1.x |
| Monthly source refresh | Observation jobs may fetch; publication still requires review. Fetch does not renew `last_human_reviewed_at`. |
