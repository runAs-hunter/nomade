## 1. Decision

Every Nomade data field belongs to exactly one **classification class** below. Each class defines purpose, sensitivity, retention, deletion, logging, AI-sharing, and backup behavior.

No new persistent field ships without a class. If unsure, treat as **Restricted** until reclassified in a revised ADR.

---

## 2. Classification classes

### Class A — Public official knowledge (published guidance inputs)

**Examples:** Registered official source URLs, fetch metadata, immutable raw snapshots (HTML/PDF bytes), extracted document versions, approved claim versions, evidence locators/excerpts, jurisdiction routing tables, review issue summaries that do not contain customer PII.

| Dimension | Rule |
|---|---|
| **Purpose** | Power citation-bound checklists and answers; prove what authorities published and when |
| **Sensitivity** | Low–moderate. Content is public, but integrity and provenance are critical. Raw snapshots may include third-party site chrome; still treat storage as internal. |
| **Retention** | Keep version history indefinitely for auditability of what the product once asserted. Superseded claims remain readable as history; they are not “answerable.” |
| **Deletion** | Do not hard-delete approved history to “clean up.” Tombstone or supersede. Raw snapshot objects are immutable; deletion only via legal takedown / documented incident process. |
| **Logging** | Log job runs, fetch outcomes, hashes, review actions. Do not log full raw HTML/PDF into application logs. |
| **AI-sharing** | Models may receive **only approved, applicable claim packages** (plus short evidence excerpts) for customer answers. Candidate/unapproved claims are never sent to customer-facing AI. Extraction models (if used offline in review pipelines) may see snapshots in staff/server context only — never via the iOS client. |
| **Backup** | Included in database + private object-storage backups. Restore must preserve hashes and immutability invariants. |

**Exposure:** `knowledge` / `operations` internal by default. Customer clients never get direct table access. Retrieval goes through reviewed `api` functions/views after K2.

---

### Class B — Account identity

**Examples:** Internal user UUID, Sign in with Apple subject, auth identity rows, session/device identifiers needed for auth, account deletion state.

| Dimension | Rule |
|---|---|
| **Purpose** | Authenticate the user; bind journey, billing, and privacy rights to one account |
| **Sensitivity** | High (PII / credential-adjacent) |
| **Retention** | While account is active. After verified deletion request: delete or irreversibly de-identify per Apple and privacy policy timelines (target ≤ 30 days unless a labelled legal hold applies) |
| **Deletion** | Idempotent account deletion workflow (F2.6). Email is not the primary key. Provider subject remains unique while active; post-deletion re-signup creates a new user UUID |
| **Logging** | Auth success/failure and denial events with internal user id / request id. Never log tokens, authorization codes, or raw identity tokens |
| **AI-sharing** | **Never** send Apple tokens, auth secrets, or full identity rows to any model provider |
| **Backup** | In DB backups; access to backup restores is staff-only and audited |

---

### Class C — Journey profile and case data

**Examples:** Applicant profile fields used for routing (citizenship, US residence/post, worker type, stay intent, family flags as product needs), case state, milestone/task instances, pinned knowledge claim/checklist versions, sync metadata, consents.

| Dimension | Rule |
|---|---|
| **Purpose** | Personalize deterministic eligibility/jurisdiction routing and the user’s task plan |
| **Sensitivity** | High (sensitive personal / immigration-context data) |
| **Retention** | For the life of the account + any labelled retention required for disputes. Soft-deleted journey rows follow account deletion policy |
| **Deletion** | User export then delete with account. Active tasks are never silently rewritten when knowledge changes — impacts are reviewable (F4.7 / P1.8) |
| **Logging** | Operational events (sync errors, conflict codes) without dumping full profile payloads |
| **AI-sharing** | Only the **minimum applicant context** required for applicability/retrieval (structured fields). Never upload user documents in V1 (document vault is deferred). Never paste free-form chat history containing secrets into logs |
| **Backup** | DB backups; restore tested in F1.9 / R1.6 |

---

### Class D — Chat and AI interaction content

**Examples:** User chat messages, model outputs, citation packages attached to an answer, “save as action” derivatives.

| Dimension | Rule |
|---|---|
| **Purpose** | Help the user understand cited requirements; optional save-to-task |
| **Sensitivity** | High (may contain personal details the user types) |
| **Retention** | Default: retain while account active for product continuity. User may delete thread/account. After account deletion: delete chat content with the account unless a labelled legal hold exists |
| **Deletion** | Support account deletion; provide in-app path consistent with Apple requirements |
| **Logging** | **Never** log raw chat/document text in analytics or standard app logs. Log counts, latency, error codes, claim IDs used |
| **AI-sharing** | Backend-only provider calls. Prompt includes approved claims + minimal context. No training opt-in that sends Nomade chats to train foundation models unless separately disclosed and approved. Provider data-retention settings must match privacy policy |
| **Backup** | If stored in DB, included in encrypted backups; excluded from product-analytics pipelines |

---

### Class E — Billing and entitlements

**Examples:** App Store transaction ids, signed notification payloads (stored minimally), derived entitlement state, usage ledger for AI quotas, refund/grace markers.

| Dimension | Rule |
|---|---|
| **Purpose** | Enforce paid access server-side; reconcile StoreKit events |
| **Sensitivity** | High (financial / account linkage). Prefer opaque App Store identifiers over card data (StoreKit — no card storage) |
| **Retention** | Append-only purchase/notification events retained for reconciliation and dispute windows (minimum 1 year recommended; align with Apple/finance needs in F3.1). Derived entitlement can be recomputed |
| **Deletion** | On account deletion: retain only what finance/legal requires as a labelled exception; strip unnecessary profile linkage where possible |
| **Logging** | Entitlement allow/deny with internal ids; no full JWS payloads in routine logs |
| **AI-sharing** | **Never** |
| **Backup** | DB backups; notification reconciliation drill in R1.6 |

---

### Class F — Customer documents (deferred V1 vault)

**Examples:** Passport scans, income PDFs, insurance certificates uploaded by the user.

| Dimension | Rule |
|---|---|
| **Purpose** | Future private vault — **out of V1 scope** until R1-stable (deferred phase V1.x) |
| **Sensitivity** | Restricted (government ID / financial documents) |
| **Retention / deletion / AI** | Defined only in a future vault ADR (V1.1). Until then: **do not build upload APIs or send user files to models** |
| **Logging / backup** | N/A until implemented |

---

### Class G — Security, audit, and operations

**Examples:** Append-only review actions, fetch job runs, alerts, authz denials, admin actions, consent records, rate-limit counters.

| Dimension | Rule |
|---|---|
| **Purpose** | Accountability, abuse detection, KB review trail |
| **Sensitivity** | Moderate–high depending on fields; avoid embedding Class C/D payloads |
| **Retention** | Audit/review trails: ≥ 2 years (or longer if required by later compliance ADR). Metrics counters may roll up |
| **Deletion** | Not user-deletable if required for security accountability; disclosed in privacy policy |
| **Logging** | This class *is* the log of record — still redact secrets and chat text |
| **AI-sharing** | **Never** send audit trails to model providers |
| **Backup** | Included; append-only semantics preserved on restore |

---

### Class H — Secrets and credentials

**Examples:** Supabase service role keys, Anthropic API keys, App Store Connect `.p8`, APNs keys, webhook secrets.

| Dimension | Rule |
|---|---|
| **Purpose** | Operate services |
| **Sensitivity** | Restricted |
| **Retention** | Rotate on schedule and on incident; keep prior secret disabled, not in git |
| **Deletion** | Rotate/revoke; never commit to repositories |
| **Logging** | Never |
| **AI-sharing** | Never |
| **Backup** | Secrets managers / Vercel env / GitHub Actions secrets only — not DB dumps |

## 3. Cross-cutting rules

1. **Separate domains:** Public-source knowledge (Class A) and private customer data (Classes B–E) share Postgres infrastructure but use separate schemas/roles and never anonymous client table access for internal tables.
2. **Answerability ≠ storage:** Storing a claim does not make it answerable. Answerable requires approved + applicable + fresh + conflict-free + evidenced (per KB design).
3. **Fetch ≠ review:** A successful official fetch must not update `last_human_reviewed_at`.
4. **Analytics:** Product analytics (if added later) use privacy-preserving events only — no chat text, no document text, no exact sensitive profile dumps (R1.2).
5. **Support access:** Support sees redacted entitlement/journey diagnostics by internal reference — not free browse of chat or future documents.
6. **Legal hold:** Only the owner (Isaias) or counsel may label a hold that pauses deletion; holds must be recorded in operations audit.

## 4. AI-sharing summary (quick reference)

| Class | Customer-facing AI | Staff extraction / review tooling |
|---|---|---|
| A approved claims + short excerpts | Allowed | Allowed |
| A candidates / unapproved | Denied | Allowed in review systems only |
| B identity | Denied | Denied |
| C profile (minimum structured context) | Allowed when required for applicability | Allowed |
| D chat | Provider call with redacted prompt policy | Denied in analytics |
| E billing | Denied | Denied |
| F documents | Denied until vault ADR | Denied until vault ADR |
| G audit | Denied | Denied |
| H secrets | Denied | Denied |

## 5. Backup and restore expectations

- F1.9: Dev snapshot restore into a clean environment; migration rollback procedure documented.
- R1.6: Production backup/restore and App Store notification reconciliation drill before public launch.
- Backups inherit classification of contained data; restore access is staff-only and audited.
