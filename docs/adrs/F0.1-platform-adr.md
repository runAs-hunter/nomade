## 1. Decision

Nomade’s V1 platform baseline is:

| Layer | Choice |
|---|---|
| Managed PostgreSQL, Auth, private object storage | **Supabase** (one project per environment) |
| Next.js API / web deploy, previews, serverless jobs | **Vercel** |
| iOS purchases and entitlements | **StoreKit 2** + **App Store Server API** / Notifications V2 |
| On-device offline cache | **SwiftData** (cache only — not the post-login source of truth) |
| In-app assistant model provider | **Anthropic**, called **only from the backend**, behind a replaceable provider interface |
| Source control / PR / CI | **GitHub** (`runAs-hunter/nomade`, `runAs-hunter/nomade-ios`) |
| iOS client | **SwiftUI** native app (existing `nomade-ios`) |

This ADR freezes vendors and boundaries for F1–P1. Changing a vendor after F1 starts requires a new ADR and a migration plan.

---

## 2. Context

Nomade is moving from a static prototype checklist and free-form visa chat into a paid, account-based journey whose guidance comes from a **monitored evidence system** (versioned official sources → human-approved claims → citation-bound answers).

Constraints that drove this decision:

- Guidance must be **traceable, reviewable, and withholdable** — not model memorization.
- Public-source knowledge and private customer data share infrastructure but must stay in **separate security domains**.
- Founder capacity is limited (~5–8 hours/week); the stack must be operable without a large ops team.
- iOS is already in progress in Xcode; the client will not be rewritten as Expo/React Native for V1.
- Prototype chat that invents unsourced figures is a product risk and must be replaced before paid/public guidance.

## 3. Environment model

| Environment | Purpose | Database | Deploy | Apple | Model keys |
|---|---|---|---|---|---|
| **Local** | Dev + migration proof | Supabase CLI + Docker-compatible runtime | `next dev` / Xcode Simulator | StoreKit config file | Local secret store only |
| **Development** | Shared integration | Supabase project `nomade-dev` (ref `veuxexnzyrgznvhdjpys`, `us-west-2`) | Vercel preview / `nomade-dev-app` | Apple development signing | Non-production Anthropic key |
| **Staging** | Pre-prod rehearsal | Separate Supabase project or approved Supabase branch (TBD in F0.3 / F1.1) | Vercel staging | Sandbox App Store | Non-production keys |
| **Production** | Paying users | Separate Supabase project | Vercel production (human-gated) | App Store production | Production keys; human-installed |

**Rules**

1. One managed PostgreSQL project (or approved branch) per environment — no sharing prod data with agents.
2. MCP / agent connectors attach to **development only**, preferably `read_only` for routine work.
3. Production migrations run from **reviewed repo migrations through CI**, with a named human approval gate.
4. No ad hoc Dashboard schema edits once migrations begin.
5. iOS never receives service-role keys. Clients may receive only publishable keys paired with tested RLS / explicit grants.
6. SwiftData holds offline cache and outbox; **canonical journey and entitlement state lives on the server** after login.

**Suggested logical schemas (physical names may follow Supabase conventions if relationships and security behavior are preserved):**

```text
identity     users, auth identities, deletion state
billing      entitlements and App Store transaction events
journey      cases, profiles, tasks, milestones, devices
knowledge    sources, snapshots, claims, evidence, review issues
operations   consents, usage ledger, audit/security events
api          minimal client/server retrieval views and functions
```

Knowledge raw HTML/PDF bytes live in a **private** object bucket; the DB stores keys and hashes only.

## 5. Rejected alternatives (for V1)

| Alternative | Why rejected for V1 |
|---|---|
| Expo / React Native rewrite | Existing SwiftUI investment; StoreKit and offline UX already on native path |
| Firebase as primary DB/auth | We need first-class Postgres, migrations, RLS, and private buckets aligned to the KB design |
| Client-direct Supabase Data API for all tables | Too easy to over-expose; V1 exposes only reviewed `api` views/functions |
| On-device-only knowledge / bundled YAML as production truth | Cannot meet citation, freshness, conflict, and review requirements |
| Free-form model “expertise” for visa answers | Highest current product risk; replaced by citation-bound retrieval (K2) |
| AWS self-managed Postgres + ECS from day one | Ops overhead exceeds founder bandwidth for V1 |
| Stripe as primary iOS billing | App Store policy for digital goods; StoreKit 2 is the correct V1 path |
| Multi-country KB in V1 schema scope | Italy DNV / remote-worker first; schema should allow expansion later without shipping it |

## 6. Cost assumptions (order-of-magnitude, V1)

Assumptions for planning — not a quote. Revisit at F1.1 and before production.

| Item | Assumption |
|---|---|
| Supabase | Free/Pro tier for early env; expect Pro once auth + storage + backups matter |
| Vercel | Hobby/Pro sufficient for preview + light API until traffic grows |
| Anthropic | Backend-only; usage gated by entitlement + rate limits; CI mocks provider |
| Apple | Standard Developer Program; sandbox before any paid cohort |
| GitHub | Private iOS repo; branch protection may require plan upgrade or compensating control (F0.5) |
| Founder time | ~5–8 h/week; prefer managed services over custom infra |

Exit cost risk is mainly **data export + auth/billing rewrite**, not compute lock-in.

---

## 7. Exit strategy

If we must leave a vendor:

| Vendor | Exit path |
|---|---|
| Supabase | Standard Postgres dump + object export; Auth identities mapped to portable user UUIDs; migrations kept in repo |
| Vercel | Next.js is portable to another Node host; keep infra-as-config in repo |
| Anthropic | Provider interface; swap model vendor without changing claim retrieval contract |
| StoreKit | Entitlements derived from append-only purchase events; retain transaction history for reconciliation |
| SwiftData | Cache can be wiped and re-synced from server; do not treat local store as archival SoT |
