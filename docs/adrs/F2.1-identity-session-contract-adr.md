## 1. Decision

Nomade V1 authentication and account lifecycle follow this contract. Implementations (F2.2–F2.7, F4.6) must not invent parallel semantics. Changing this contract after approval requires a revised ADR.

| Topic | Locked rule |
|---|---|
| Primary sign-in | **Sign in with Apple** via **Supabase Auth** (no password login in V1) |
| Canonical user id | Server-issued **UUID** (`users.id`) — **not** email, not Apple `sub` alone |
| Auth binding | `auth_identities` row: `(provider, provider_subject)` unique while active |
| Email | Optional / Apple-relay; never primary key; never used alone for authorization |
| Session proof | Supabase-issued JWT (access token); backend verifies signature + claims before any private data |
| Anonymous preview | **Local-only** until first successful Apple sign-in (no server user row) |
| Service role | Backend only; never shipped to iOS or browser clients |
| Deletion | Idempotent request; Class B delete/de-identify ≤ 30 days unless labelled legal hold (F0.2) |
| Re-signup after deletion | New `users.id`; old Apple subject may reappear only after prior identity row is closed per deletion workflow |

## 2. Context

F1 delivered roles/RLS, Preview→`nomade-dev`, logging envelope, and a backup drill. F2 starts by freezing **who a user is** and **how sessions are proven** before Sign in with Apple wiring (F2.2), migrations/bootstrap (F2.3), or iOS UI (F2.4).

Threat-model drivers (F0.6): stolen device (AC-01), token leakage (AC-02), IDOR (AC-03), anonymous→Apple merge collision (AC-04), incomplete deletion (AC-05).

## 3. Actors and identifiers

| Identifier | Where | Rules |
|---|---|---|
| `users.id` | Postgres `identity` (or equivalent schema) | Stable UUID; cited in logs as `userId`; never guessable from email |
| `auth.users.id` (Supabase) | Supabase Auth | Maps 1:1 to app `users.id` **or** is the same UUID — document chosen mapping in F2.3; do not maintain two conflicting “user ids” for the same login |
| `provider` | `apple` | V1 only Apple; other providers require ADR |
| `provider_subject` | Apple `sub` | Unique among **active** identities; store hashed or raw per F2.3 (prefer store opaque `sub` as text; never log it in full if avoidable — log prefix only) |
| `device_id` | Client-generated UUID in Keychain | Used for sync/device rows later (F4); **not** an auth credential |
| Access token | Authorization: Bearer | Short-lived; Keychain on iOS; never logs/analytics |
| Refresh token | Supabase session | Keychain only; refresh via Supabase SDK; never sent to Anthropic or third parties |

---

## 4. Anonymous preview (pre-account)

1. Before Apple sign-in, the app may collect **local** journey draft data in SwiftData (prototype path).
2. **No** `users` row, **no** server journey, **no** entitlement is created for anonymous preview.
3. Anonymous clients may call only explicitly public/unauthenticated endpoints (health, future public marketing). They **must not** receive service-role powers or read other users’ data.
4. Anonymous local data is **not** Class B account identity until merge/bootstrap succeeds.

---

## 5. Sign-in and bootstrap (happy path)

```text
iOS Sign in with Apple → Apple identity token
  → Supabase Auth (Apple provider) → session (access + refresh)
  → iOS calls backend bootstrap (Authorization: Bearer <access>)
  → Backend verifies JWT (issuer, audience/project, exp, sub)
  → Upsert auth identity + ensure exactly one users row (idempotent)
  → Return { userId, created: bool, merge: … }
```

**Bootstrap invariants (F2.3 implements):**

1. First valid login creates **one** user; retries with the same provider subject return the **same** `userId` (idempotent).
2. Provider subject uniqueness is enforced in DB (unique index on active identities).
3. Email never decides which account you get.
4. Bootstrap does **not** require a paid entitlement.
5. Response never includes refresh tokens, service-role keys, or raw Apple authorization codes.

---

## 6. Token validation (F2.5 implements; contract now)

Protected API routes:

1. Require `Authorization: Bearer <jwt>`.
2. Verify JWT with Supabase JWT secret / JWKS for the **current environment** (`nomade-dev` vs `nomade-prod` — never accept prod tokens on Preview/dev).
3. Reject missing, expired, wrong-issuer, wrong-audience, and malformed tokens with stable codes (see §10).
4. Resolve `userId` from verified `sub` → identity map; if no app user yet, only bootstrap may create one.
5. Authorization is **user-scoped**: resource `user_id` must equal authenticated `userId` (plus RLS). Cross-user access → `FORBIDDEN` (never empty 200).
6. Health remains public (no auth). Future rate limits (F2.9) do not replace auth.

## 7. Merge behavior (anonymous local → Apple) — account level

This section freezes **account** merge semantics. Journey field-level conflict UI is detailed in **F4.6**; it must obey this ADR.

### 7.1 Definitions

| Case | Meaning |
|---|---|
| **A** | Local anonymous draft exists; Apple account is **new** (no prior server journey) |
| **B** | Local anonymous draft exists; Apple account **already** has server journey data |
| **C** | No local draft; Apple account new or existing | Normal bootstrap / resume |
| **D** | Same Apple subject already linked | Idempotent bootstrap; no second user |

### 7.2 Rules (proposed defaults — confirm in approval)

1. **Case A — auto-attach:** After successful bootstrap, client may upload local draft to **that** `userId` via later sync APIs (F4). Server never invents a second user for the draft. Merge operation is **idempotent** (replay safe).
2. **Case B — user choice required (no silent overwrite):** Do **not** auto-replace server journey with local, and do **not** auto-discard local without consent. V1 choices presented once:
   - **Keep server** (discard local draft), or
   - **Replace server with local** (server journey tombstoned / superseded per F4; irreversible after confirm).
   - “Keep both” is **out of V1** (would imply multi-case accounts).
3. **Case C:** No merge step.
4. **Case D:** Same `userId`; ignore duplicate merge requests.
5. Merge never runs across **different** Apple subjects. Account takeover via merge is forbidden.
6. Billing entitlements always follow the **Apple-linked** `userId`; local anonymous never “inherits” a stranger’s subscription.

### 7.3 Explicit non-goals of F2.1 merge

- Multi-device conflict resolution details (F4.2 / F4.6)
- Family Sharing Apple ID edge cases (F3.1)
- Admin-assisted account merge

## 8. Sign-out, recovery, deletion

| Event | Behavior |
|---|---|
| **Sign out** | Clear Keychain session; stop authenticated API calls; local cache may remain until next login/wipe policy (F4) |
| **Token expiry** | Refresh via Supabase; on refresh failure → signed-out UX; no silent privileged calls |
| **Relaunch** | Restore session from Keychain if valid; otherwise signed-out |
| **Delete account** | In-app request (Apple requirement); backend marks deletion + enqueues wipe (F2.6); reauth required before delete (AC-01) |
| **Export** | User-scoped bundle before/at deletion (F2.6); no other users’ data |
| **Recovery** | Support cannot “restore password”; user re-signs with Apple. Post-deletion: new account, empty journey unless legal hold restores staff-only archives (not customer self-serve) |
| **Retention exceptions** | Only labelled holds (F0.2 §3.6); billing append-only rows may retain stripped identifiers (Class E) |

## 10. API surface (contract sketch — F2.3/F2.5/F2.6 fill paths)

Exact paths may use `/api/v1/...` once versioning lands; until then prefer `/api/...` consistent with health.

| Endpoint (conceptual) | Auth | Purpose |
|---|---|---|
| `POST /api/account/bootstrap` | Bearer | Idempotent ensure user + identity; return merge hints |
| `GET /api/account/me` | Bearer | `{ userId, createdAt, deletionStatus }` — no tokens |
| `POST /api/account/sign-out` | Bearer optional | Server-side session revoke if used; client always clears Keychain |
| `POST /api/account/export` | Bearer + reauth | Start/download export (F2.6) |
| `POST /api/account/delete` | Bearer + reauth | Idempotent deletion request (F2.6) |

**Stable error codes** (extend F1.8 envelope):

| Code | HTTP | When |
|---|---|---|
| `UNAUTHENTICATED` | 401 | Missing/invalid/expired token |
| `FORBIDDEN` | 403 | Authenticated but not allowed (IDOR, wrong user) |
| `MERGE_REQUIRED` | 409 | Case B — client must present choice before sync upload |
| `ACCOUNT_PENDING_DELETION` | 403 | Account in deletion window; limited ops only |
| `ACCOUNT_DELETED` | 401/410 | Identity closed; must sign up fresh |
| `BAD_REQUEST` | 400 | Malformed body |
| `INTERNAL_ERROR` | 500 | Unexpected |

Success bodies never echo Authorization headers or Apple identity tokens.

## 11. Logging and privacy (F0.2 / F1.8)

- Log `requestId`, `userId` (internal UUID), auth allow/deny reason codes.
- Never log access/refresh tokens, Apple authorization codes, full `sub` if avoidable, email, or profile payloads.
- Auth denial events feed F2.10 later; shape logs so F2.10 can subscribe without parsing PII.
